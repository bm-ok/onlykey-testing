# The composite PQC keys use private-range algorithm IDs, so nothing else can read them

**Component:** the vendored PQC openpgp.js fork — `onlykey.github.io`
(`src/onlykey-fido2/onlykey/vendor/openpgp/openpgp.js`) and the byte-identical
copy in `python-onlykey/onlykey/openpgp_bridge/openpgp.js`.

**Severity:** interoperability. Not a memory-safety or key-disclosure bug, and
nothing about it is insecure. It is here because it is the one defect in this
set that **cannot be fixed after a release** without invalidating every key and
every message the release produced.

## What was measured

A composite key generated by the web app's own `generateCompositeKey()`, dumped
straight out of the armor rather than through any library's own reader:

```
key packet version 6
ALGORITHM BYTE ON THE WIRE = 107      (primary,  ML-DSA-65+Ed25519)
ALGORITHM BYTE ON THE WIRE = 105      (subkey,   ML-KEM-768+X25519)
```

The IANA "OpenPGP Public Key Algorithms" registry assigns:

| ID | algorithm |
|----|-----------|
| 30 | ML-DSA-65+Ed25519 |
| 31 | ML-DSA-87+Ed448 |
| 32-34 | SLH-DSA-SHAKE-{128s,128f,256s} |
| **35** | **ML-KEM-768+X25519** |
| 36 | ML-KEM-1024+X448 |

105 and 107 are not in that registry. They fall inside **100–110, the private /
experimental range**, which the spec reserves for exactly what the name says:
private use, with no expectation that anybody else can interpret them.

So the two codepoints this release ships are not the ones the standard assigns,
and the mismatch is in the key packet itself — the very first thing any other
implementation parses.

## Why it was not caught

Everything that has ever read one of these keys is the same codebase. The web
app vendors the fork; `python-onlykey`'s bridge vendors a **byte-identical**
copy (its own `VENDORED.md` says so, "confirmed via `diff` at vendor time").
A test that generates with one and parses with the other agrees perfectly and
proves nothing about the wire format — which is the same trap
`02-cli/15-age-file-interop` was written to escape for the age container.

`VENDORED.md` also states the codepoints as fact:

> the composite-KEM combine/AES-keywrap math for
> `pqc_mlkem_x25519`/`pqc_mldsa_ed25519` (IETF OpenPGP-PQC draft algos 105/107).

That sentence is wrong, and it is the reason nobody re-checked. The draft's
codepoints are 30 and 35.

## What three independent implementations do

Every one of these was installed from source this session, into a
workspace-local prefix, and asked to read the key above.

| implementation | spec line | key version | ML-KEM composite | ML-DSA composite | reads our key? |
|---|---|---|---|---|---|
| **ours** (vendored openpgp.js fork) | private codepoints | v6 | **105** | **107** | — |
| **rpgp 0.20** (`draft-pqc`) | draft-ietf-openpgp-pqc / IANA | v6 | **35** | **30** | no — unknown algorithm |
| **GnuPG 2.5.21** + libgcrypt 1.12.2 | LibrePGP | v5 | **8** (`kyber768_cv25519`) | none at all | no — cannot parse v6 |
| **BouncyCastle 1.85** (`bcpg`) | RFC 9580, no PQC | v6 | none | none | no — no PQC in its OpenPGP layer |

GnuPG's refusal is the blunt one, and it is not about codepoints:

```
$ gpg --import onlykey-composite-pub.asc
gpg: packet(6) with unknown version 6
gpg: read_block: read error: Invalid packet
gpg: import from 'onlykey-composite-pub.asc' failed: Invalid keyring
gpg: Total number processed: 0
```

GnuPG 2.5.21 has no RFC 9580 v6 key support at all — its only related option is
`--rfc4880bis` — and its PQC is the LibrePGP line: `kyber768_cv25519` on a **v5**
key packet at codepoint 8, with **no ML-DSA of any kind** (`Pubkey: RSA, Kyber,
ELG, DSA, ECDH, ECDSA, EDDSA`). So GnuPG is two independent steps away and will
not be an interop target for this design on any timescale worth planning around.

**rpgp is the one that matters.** It is a genuinely independent implementation
(Rust, RustCrypto primitives, never saw this project's code) that implements the
same draft we are targeting, on v6 keys, with the same composite construction.
It is the closest thing to a conformance oracle that exists today, and the only
thing standing between it and a full round trip is two bytes.

## What it would take

Change the two codepoints to 30 and 35 in the fork, in both vendored copies, and
in the places that mirror them:

- `composite_pgp.js` — `PQC_KEY_TYPE_BYTE` is the *device* slot type (0x67) and
  is unaffected; the OpenPGP algorithm IDs live in the fork's `enums.publicKey`.
- `python-onlykey/onlykey/pqc.py` and `libagent/device/onlykey_pqc.py` both name
  `MLKEM_ALGO_ID = 105` in their composite-KDF framing, which is fed into the
  KMAC combine — so it is not only a tag, it is **bound into the key derivation**
  and changing it changes every derived session key.

That last point is why this is a pre-release fix. The algorithm ID is an input
to `KMAC256("OpenPGPCompositeKDFv1", ...)`, so keys and messages made before and
after the change are mutually unreadable even once both sides agree on the tag.
Shipping first and correcting later means a flag day for every user who
generated a key in between.

**Nothing about the device changes.** The firmware stores four raw seeds and
performs ML-KEM decapsulation and ML-DSA signing on them; it never sees an
OpenPGP algorithm ID. This is entirely a host-side framing fix, which is the
good news in it.

## What this does NOT say

It does not say the cryptography is wrong. The KEM combine, the key wrap, the
ML-DSA framing and the device's arithmetic are all verified against
independently computed values in `02-cli/06-composite-ops` and
`02-cli/17-composite-cli-ops`, and they are correct. A key with the right
codepoints on it would, on this evidence, be expected to interoperate.

It also does not say rpgp would accept the result today — that has not been
measured, because it cannot be until the codepoints change. What has been
measured is that rpgp implements the same draft and rejects our key for exactly
this reason and no other.
