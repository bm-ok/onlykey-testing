I want to build a test kit for OnlyKey that runs against the emulator first and physical hardware second. The old kit, `onlykey-alpha-testing`, was designed before the emulator existed, so it assumes a real key on a real USB bus and it assumes a human is watching the terminal. Neither assumption holds any more. This kit is a redesign, not a port: the test cases carry over in spirit, but nothing else does.

Three problems drove this. Hangs are invisible - nw.js can wedge with no attributable step, and mocha's per-test timeout does not actually cancel anything, so a hung device call keeps running and leaks into the next file. Completion and crashes look identical - a firmware segfault, a wedged browser, and a clean pass all present as "the command stopped producing output", which is exactly the state an automated agent cannot recover from. And device state cross-contaminates, so files have to be run one at a time. Those are the three things this kit exists to fix, and every design decision below traces back to one of them.

## What the emulator makes possible

The emulator changes what is possible. `native.sendHid()` and the `'stream'` event are a full-duplex in-memory HID bus - no dummy_hcd, no configfs, no root, no USB at all. The gadget bridge is just one consumer of that bus, not a requirement. That is what makes this runnable in a GitHub Actions workflow on a stock hosted runner, which is the actual goal. And `flash.bin` / `eeprom.bin` are ordinary files, so device state can be snapshotted and restored instead of being rebuilt by driving the PIN state machine every time.

One host setting decides how much of the device is reachable, and it has to be stated up front because it silently changes what a test run even means. The firmware reads its own storage through raw pointers, so the emulator maps `flash.bin` at its real address, and `vm.mmap_min_addr` decides how low that mapping can start. There are three rungs. At `0x0000` everything works, including `fw_hash()`'s walk from `fwstartadr`. At `0x1000` - the setting to actually use - the firmware's key material at `certified_hw` (`enckeysectoradr+432`, `0x5BB0`) is mapped, so crypto works, and page zero stays unmapped so a genuine NULL dereference still faults exactly as it should. At `0x10000`, the unprivileged default, storage at `0x3A800` is reachable and the device boots and enumerates, but `okcrypto_split_sundae()` dereferences `certified_hw` on every AES-GCM operation, so the device segfaults the moment it encrypts anything - storing a PIN included. That rung is HID and protocol work only, and a run that lands there must say so rather than reporting a pile of crashes. The runner therefore reads back which rung it got and treats it as a capability, the same way it treats everything else it cannot do.

## The kit runs in two processes

The kit runs in two processes, and this is not a preference. `CPU_RESTART()` ends the firmware thread, and `start()` cannot be called a second time in the same process: `okemu_hal_shutdown()` never unmaps, so the second `okemu_hal_init()` collides on `MAP_FIXED_NOREPLACE`; re-arming the restart trap saves its own handler as the "previous" one, which turns any later genuine crash into a fault loop; the ThreadSafeFunctions leak; and the firmware's C++ globals were constructed once at dlopen and never reconstruct. These tests reboot constantly, so the test code cannot live in the emulator's process. The runner is the parent and holds all test code. The device host is a child, and it is `bin/daemon.js` with the gadget bridge taken out: it requires the emulator, calls `start({storageDir})`, runs the existing IPC peer as its whole body, and writes the restart marker described below. `device.restart()` means the child dies and the parent respawns it against the same storage dir while the test carries on. That is also precisely what USB re-enumeration looks like from a hardware test's point of view, so the same API covers both transports when the hardware adapter lands.

## The channel between them

The two processes talk over the emulator's existing IPC, not a new protocol. `emulator/lib/protocol.js` is already newline-delimited JSON with base64 binary, a framer with a runaway guard, and a vocabulary that already covers presses, `writeHid`, restart and state. More importantly `ipc-host.js` already has the inverted topology this design needs - the long-lived process listens and the restarting process dials in - for exactly the stated reason that a reboot then becomes an ordinary client disconnect. Reusing it also avoids a stdio pipe, which would deadlock: the firmware is chatty in DEBUG builds, and if the parent ever stops reading, the child blocks in `write()`, its event loop stops, commands go unanswered, and the run "hangs" for a reason no watchdog can name.

Reusing it means inheriting four rough edges, and they are cheap to absorb in the adapter and expensive to discover at three in the morning. `IpcHost.writeHid(iface, data)` takes its arguments in the opposite order from `emu.writeHid(buffer, iface)`, so anything that touches both layers gets them backwards exactly once. `IpcHost` has no `setPlugged` sender even though the peer handles the command, so a bus-only detach - the thing a hardware unplug test wants - has to be sent raw. The `'error'` event carries two unrelated things, a transport `Error` object and a device-sent `{t:'error', message}` frame, because `_onFrame` re-emits every frame under its own type name; a listener that assumes either shape is wrong half the time. And `listen()` probes an existing socket file by spawning a whole Node process, which costs up to two seconds, and then throws if something already answers there - a running GUI, most likely. So each run gets its own socket path inside its own run directory. That removes the collision, removes the probe, and lets two runs coexist.

One peer behaviour has to be known by anything consuming the stream: outbound SEREMU and keyboard traffic is deliberately suppressed from the `hid` frames, because it already leaves as `log` and `keyboard` and would otherwise be doubled. Inbound keyboard frames are forwarded, since the host's LED reports have no other message. Reading `hid` alone therefore loses the entire debug console without saying so.

## Telling the ways the device host can die apart

Distinguishing the ways the device host can die is the part that has to be exact, because today an expected restart and an OOM kill are byte-identical to the parent - both are `code:null, signal:'SIGKILL'`. So the child writes a generation-stamped marker file synchronously before it kills itself, and the parent classifies on the child's `exit` event rather than on the restart message. SIGKILL with a marker is an expected restart and the run continues. SIGKILL without one is an external or OOM kill and the run aborts. SIGSEGV is a firmware crash, and the firmware already writes `[okemu] FATAL: segfault at` plus a backtrace to stderr, which gets attached to whichever test was running. A failure to map at startup is a separate case again and is a retry rather than a device crash, because a run legitimately produces hundreds of restarts and even a small per-boot failure rate becomes a run-killer at that count. In practice this should be rare: the collision that used to crash-loop the daemon was the thirty-two megabyte bit-band alias fighting V8's ASLR'd heap, and that region is already marked optional and skipped when its address is taken, leaving two required one-megabyte windows that seldom collide. The retry is a backstop, not an expected event, and it is counted so that it stops being invisible if that ever changes. Respawning on the exit event rather than the restart message also avoids two children racing the same `eeprom.bin`, since the old child writes the whole EEPROM during shutdown.

## How a test file is written

A test file is written with `describe` and `it`, the way `harness.js` already works, and is flat - one suite per file, no nesting. What a file adds is a small block of metadata alongside its name, saying which device state it needs and which capabilities it requires, so the runner can prepare the device and can skip a file with a stated reason rather than failing it obscurely when a capability is missing. Registration is a side effect of loading the file, which is fine because the runner loads exactly one file at a time and clears the registry between files; that per-file isolation is also what keeps one suite's failure from renumbering another's. Each test receives one argument holding the device handle, the assertions, a logger, a skip function, and an AbortSignal that every wait honours, so that a timeout genuinely cancels rather than leaving the test running while the runner moves on.

## The harness

`harness.js` is the test harness. It was written earlier for driving tests from inside an app and is brought over here deliberately, because its shape is already the right one and is the reason mocha is not wanted: suites and tests are plain registrations, assertions are three small functions rather than a chained expectation language, everything a test needs is injected into it rather than reached for through globals, and a run returns a data structure instead of printing at a human. That last property is what the whole reporting design rests on - the run result is already the verdict, so the exit code and the sentinel line are read off it rather than reconstructed from output.

Several things the design needs are already there and should be used rather than rebuilt. The per-test callbacks report a test starting, finishing, and changing status, which is exactly the signal the status file needs, so live progress is a listener rather than new machinery. The injected context is how the device handle reaches each test. The test filter is how a single file or a single test gets selected from the command line. The registered-suite listing is how the runner can enumerate a file's tests. The absence of `before`/`after` hooks is not a gap either - it is the same decision as running services from visible test files, and adding hooks would reintroduce exactly the invisible step this kit is trying to eliminate.

What has to be added is the part it was never asked to do, because nothing about running inside an app required it. A real cancellation path, since today a timeout races the test and lets the loser keep running. Clearing the registry between files so each file is isolated. Stopping at the first failure. The metadata block on a suite. A `skip` function, which the injected context is supposed to carry and currently does not. A result shape that can represent a skip at all, because the existing filter drops a test out of the results entirely rather than recording it as skipped with a reason. Per-test timing, which does not exist today and which both the status file's elapsed time and the per-test deadline need. And around all of it, the loader, the command-line entry point, the log and status files, the sentinel, and the device lifecycle. The assertion set grows only as tests actually need it.

## One device API, two adapters

There is one device API with two adapters behind it, and two differences must be hidden inside the adapters rather than pushed onto test code. The first is the report ID: the proven hardware client always prepends a zero byte, but the emulator's delivery path pads to 64 and does not strip a leading report ID, so identical test code would put different bytes on the wire in each mode. Payloads therefore carry no report ID and the hardware adapter adds it. The second is chunking and zero-padding: the firmware already emits exactly 64 bytes for RawHID and already flushes SEREMU at 64 bytes or at a newline, and the bridges re-chunk and pad only because a hidraw reader must read the descriptor's declared count. The emulated path replicates none of that, and the hardware adapter strips the padding on the way in, so both normalise to the same line stream.

## Log handling

Log handling copies the old kit's idiom rather than improving on it. `lib/hid.js` appends everything to one accumulator string and regex-matches the whole thing, and it counts matches because the firmware emits one acknowledgement per byte sent, not one per line - a first-match wait is simply the wrong instrument for a burst of six button presses. Matching against the unsplit stream is also what the readiness probe depends on. Two further behaviours transfer with it and are easy to lose by accident: a wait matches retroactively against everything already in the accumulator, not only against what arrives after it, and clearing the accumulator is the caller's job, so a test that wants a clean slate has to ask. All of that transfers directly onto the emulator's `'log'` event. Two things do not transfer: filtering out NUL bytes destroys legitimate ones and belongs only on the hardware path, and the accumulator is unbounded and needs a cap with a rolling tail.

## Device state and fixtures

Device state comes from named fixtures with one definition and two consumers. A state module exports a check and an apply. On the emulator, apply runs once in a fixture builder and the resulting flash and eeprom images are saved with a fingerprint; each test file then boots from a fresh copy, which is what removes the cross-contamination. On hardware, the same module checks the device and runs the real setup flow if the check fails, because a physical key cannot have an image pushed into it. The fingerprint covers the built firmware archive and the upstream source revisions, and a mismatch rebuilds automatically - the old kit's on-disk caches went stale after a reflash and there is no reason to inherit that.

The images must be copied to a temp name and renamed, with sizes asserted. The loader validates size and nothing else, and on any mismatch - too short or too long - it truncates the file to zero and rewrites the whole thing with `0xFF`. A half-copied snapshot does not come back half-restored; it comes back as a factory-blank device, and the test that then fails will be blamed on the firmware.

Fixtures are built with the firmware's own wipe path rather than the addon's `factoryReset()`. That function erases the backing store behind the firmware's back, so none of the firmware's own bookkeeping happens and nothing is printed; it sets an internal restart flag that no code anywhere reads, so it never fires the restart sink and never reboots; and it erases only from the first mapped byte upward, which means on any host with a non-zero `mmap_min_addr` the low region of `flash.bin` survives the "factory reset" entirely. The firmware's own `0C` and `9C` paths do the real thing and end in `CPU_RESTART()`.

## What a snapshot cannot restore

Four limits of snapshot restore are worth stating now rather than discovering later. A snapshot always boots locked, because the unlocked/initialized/configmode flags and the PIN hashes are RAM rebuilt in `setup()` - snapshots skip provisioning, not unlocking, so every file still pays one PIN entry. FSEC is not in `flash.bin`; it lives in an anonymous peripheral mapping written fresh every boot, and what gets written depends on whether the flash mapping landed at address zero. It does not, on any host configured the way this project recommends: reaching zero needs `vm.mmap_min_addr=0` or `CAP_SYS_RAWIO`, and 4096 is the deliberate choice precisely so that page zero stays unmapped and NULL dereferences still fault. So FSEC latches to the already-provisioned value, the firmware's one-time provisioning branch never runs, and there is no factory key derivation, no firmware hash written to EEPROM, and no security lock bits. Attestation and firmware-integrity behaviour are therefore not testable in emulated mode - not because emulation cannot do it, but because the configuration that would allow it is one nobody should run - and that belongs in the capability set rather than on a bug list. And time is RAM-only and rebased every boot, so anything counter or TOTP derived needs the time re-sent after every boot, snapshot or not.

## What a run emits

Everything an automated agent needs to know is emitted unambiguously. Every run writes its own log file, so nothing has to be piped or tailed. A status file is updated live with the current section, file, test, elapsed time and failures so far, so progress can be read by polling a single file. And every run ends with exactly one sentinel line, emitted from the uncaught exception handler, the unhandled rejection handler and the exit handler alike, saying whether it finished or aborted, why, and with what code. The absence of a sentinel means a hard crash, and that single fact - answerable by one grep - is what the old kit could never provide. Failure blocks are self-contained and carry the wait that was pending, the recent device output, and the boot generation, so there is nothing to go hunting for.

The exit code says what kind of problem it is without reading anything else. Zero is a run that finished with everything passing. One is a run that finished with at least one test failing, which is the only code that means the device behaved and the software did not. Two is a firmware crash. Three is a watchdog, whichever of the three fired. Four is a harness or runner error - a file that would not load, a fixture that would not build, a configuration that does not make sense - meaning the kit failed before it could judge anything. Five is the device host dying for a reason that is not the firmware's fault, an external or OOM kill or a mapping failure that outlived its retries. Zero through three are verdicts about the device; four and five say the run did not produce a verdict at all, and that distinction is the whole point.

## Fail-fast

Fail-fast is the default. Three watchdogs bound a run: a per-test deadline, a no-progress inactivity budget, and a run-level maximum. A watchdog must report where it was blocked - which request was pending, when the last device output arrived, what it was waiting for - because otherwise a stalled transport and a genuinely slow device look the same, which is the failure mode this whole kit is designed to eliminate.

## Four sections, in order

Tests are grouped into four sections that run in order. The first is protocol testing, driven entirely from Node over the wire protocols - the debug console, the vendor interface, FIDO, keyboard capture, and pure-JS crypto vectors. The second is CLI testing through the Python venv. The third is GUI testing through nw.js. The fourth is the OnlyKey app, which runs in its own nw.js and has never been approached. Long-lived services are started and stopped by explicit test files at the start and end of their section, rather than by invisible hooks, so a wedge is always attributable to a visible step and a stop is always a step that can be seen to have run or not run. Service cleanup tracks process groups rather than bare PIDs, because nw.js can crash and leave the web app server it spawned alive as an orphan holding a port.

Only the first section is built now. The others get declared directories and stubs so the structure is fixed, but the emulator comes first and the CLI, GUI and app sections follow once the runner has proven itself. The hardware adapter is a declared seam with a stub behind it - designed for, not yet written.

## Continuous integration

Continuous integration is the reason for all of this, and it draws a hard line that is worth stating plainly: in a GitHub workflow the only thing that can run is code that reaches the device entirely inside the process. There is no USB, so nothing enumerates. There is no gadget, because dummy_hcd is not shipped by Ubuntu and would have to be compiled out of tree against kernel sources matching the runner's own kernel, which is not reliably available. There is no display, so nothing that needs a browser runs. And critically, there is no kernel HID device at all - no `/dev/hidraw`, no `/dev/hidg`, nothing for hidapi to open. That rules out far more than the GUI. It rules out node-hid, and therefore the entire hardware adapter. It rules out python-onlykey and lib-agent, because they find the device through hidapi like every other real client. It rules out the web app and the OnlyKey app, because they reach the device through the browser's own HID and WebAuthn stacks. Sections two, three and four are not merely deferred on hosted runners - they are permanently impossible there, and the workflow should say so with a stated reason rather than pretending they were skipped for convenience.

What survives is exactly one thing: tests written against the emulated adapter, which talks to the firmware over the in-process bus and never opens a device node. That is the real admission test for the first section - not "is this protocol-level" but "does this reach the device without a kernel device node". Anything that fails that test belongs in a later section even if it feels like protocol work. The upside is that the surviving set is larger than it first appears, because the emulator exposes things a kernel device never could: the keyboard interface is an event rather than a device to be read with elevated privileges, which is what finally makes backup and restore testable at all. On a hosted runner the requirements come down to `sudo sysctl -w vm.mmap_min_addr=4096`, three source checkouts, and building the addon. That exact value matters: leave it at the unprivileged default and the device still boots and still answers HID, so the workflow looks like it is working right up until the first test that stores a PIN, which segfaults. The workflow asserts the rung it got before it runs anything. Everything else - gadget mode, the CLI sections, the GUI sections, and physical hardware - belongs to a self-hosted runner or a developer's workstation, and the same test files run there unchanged through a different adapter.

## Layout and baseline

The kit is its own repository and lives beside the other checkouts under `onlykey/`, which is a swap slot rather than a dependency, so it must not assume anything about where it was cloned. It finds the emulator at `../../emulator` relative to its own root, with `OKEMU_ROOT` overriding, and if neither resolves it says which paths it tried instead of surfacing a bare module-not-found from three frames down. It is CommonJS on the same Node that built the addon, because the device host loads that addon directly and a mismatched ABI is not a failure worth debugging twice.

The command-line entry point lives in `bin/`, and `lib/` holds the runner, the device API and its two adapters, the fixture builder, and the reporting. Tests live under a directory per section, numbered so the order is visible in the tree rather than encoded somewhere else, with the three later sections present as declared directories and stubs from the start. Built fixtures are cached outside the test tree and keyed by fingerprint. Each run gets its own directory holding its log, its status file, its socket, and its restart markers, which is what makes concurrent runs and post-mortem reading both work without a special mode.
